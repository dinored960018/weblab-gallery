# REVIEW — BOC.STUDIO

- **어워드**: Awwwards Site of the Day (2026-09-19, 7.23/10 · Developer Award 7.3/10) · https://www.awwwards.com/sites/boc-studio
- **모작**: `Garfi.Studio` — 홈 · 목록 · 케이스 9 · 404 = 12페이지 (`build.mjs` + `data.mjs` 생성)

## 왜 상을 받았나

- **가장 위험한 선택**: 포트폴리오 첫 화면에 작업 썸네일 그리드도, 소개 문장도 없다. 쇼릴 영상 위에 **주황 띠 한 줄**만 가로지른다. 방문자는 무엇을 눌러야 할지 안내 없이 스크롤하거나 클릭해야 한다(커서에 붙은 "Click to enter" 알약이 유일한 안내). 그런데 첫 입력 한 번에 그 띠가 800 ms 동안 끝으로 갈수록 빨라지며 화면 맨 위로 붙어 **그대로 헤더가 되고**, 띠 위 로고 하나가 헤더 로고 자리로 날아간다. 인트로와 사이트 골격이 같은 물건이라 "인트로 건너뛰기"가 필요 없다. Awwwards 설명 "Structure first, delight throughout" 그대로다.
- **가장 많은 공이 들어간 곳**: 헤더 띠. 로더(로고 scale 4→1)·인트로(가운데 61 px)·헤더(위 38 px)·INFO 패널의 경첩이 전부 이 띠이고, 그 위에 WebGL 변위까지 얹었다. 띠를 2D 캔버스에 매 프레임 다시 그려(`fillText` 1만 8천 회) 텍스처로 쓰고, 칸마다 오프셋을 줘서 포인터가 지나가면 띠 조각이 네모나게 찢겼다가 돌아온다. 원본 셰이더 주석에 "0 을 128 로 인코딩하지 않으면 띠 전체가 반 픽셀 밀려 유리 띠처럼 보였다"는 디버깅 기록이 남아 있을 정도로 이 한 줄에 공을 들였다.
- **모작해보고 알게 된 것**:
  1. 진입 곡선은 표준 이징이 아니다. rAF 로 띠 위치를 매 프레임 재 보니 800 ms 중 절반이 지나도 8 % 밖에 안 움직이고 마지막 16 % 동안 46 % 를 움직인다. 로더의 주황 덮개 수축도 같은 성격(700 ms 에 43 %). "천천히 떠나다 확 붙는" 가속이 사이트의 손맛이다. 모작은 표본 13점을 표로 옮겨 보간했다.
  2. 목록 행의 호버 확대는 `transform: scale` 이 아니라 **높이·폭 전환**이다(188.78 → ×1.2 + 캡션 18 + 여백 15 = 259.5). 캡션이 접히는 만큼을 사진이 먹어서 행 높이는 37.5 px 만 늘고, 사진 사이 간격 15 px 은 그대로다. scale 로 흉내 내면 간격까지 커져서 다른 화면이 된다. 그래서 impeccable 의 layout-transition 경고를 받아들이고 원본 방식을 따랐다.
  3. 케이스 사이드바는 스크롤 위치에 따라 **다른 카드**를 띄운다. 처음 33 % 는 최신 프로젝트 카드, 48 % 부터는 프로젝트 유형(Refresh/Create/Boost)마다 다른 문장의 문의 카드. 첫 캡처에서는 놓쳤고, 모션 비교표의 "원본에만 있는 700 ms 페이드 div ×2" 를 추적하다 찾았다. 비교표가 없었으면 빠뜨렸을 기능이다.
  4. "유리구슬 3D" 로 적혀 있던 리서치 메모는 쇼릴 영상 속 장면이었다. 3D 여부는 스크린샷이 아니라 컨텍스트 목록(`getContext` 후킹)으로 판정해야 한다.

## 장점

- **무엇**: 목록 = 마퀴 행 9개.
  **왜 작동하나**: 프로젝트마다 한 행, 행마다 그 프로젝트 사진 9~31장이 서로 다른 속도(34~123 s)로 흐른다. 속도 차이 때문에 화면 전체가 같은 방향으로 흐르는데도 행끼리 어긋나 단조롭지 않고, 한 화면(1440×900)에 행 3.5개가 들어가 스크롤 두 번이면 전부 본다. 호버하면 그 행만 커지고 캡션이 사라져 "지금 보는 행"이 분명하다.
- **무엇**: 사이드바 분리.
  **왜 작동하나**: 왼쪽 371 px 가 목록에선 필터, 케이스에선 제목·챕터 아코디언이 되고 항상 sticky 다. 케이스 오른쪽은 글 없이 사진만 1054 px 폭으로 이어지고, 글은 사이드바에서 스크롤 위치에 맞춰 챕터 하나만 열린다. 긴 케이스(최대 16 416 px)에서도 지금 어느 챕터인지 한 줄로 보인다.
- **무엇**: 끝 처리.
  **왜 작동하나**: 마지막 392 px 동안 본문이 어두워지며 다음 프로젝트 푸터가 올라온다. 다음 이름·사진 마퀴·"View all projects"·주황 문의 띠가 한 화면에 있어 막다른 끝이 없다(9개 순환).
- **무엇**: 색 두 개.
  **왜 작동하나**: `#ff4421` 과 `#181d21` 만 쓴다. 주황은 띠·INFO·404·문의처럼 "스튜디오가 말하는 곳"에만, 사진이 없는 면은 전부 어두운 바탕이라 고객 작업 사진의 색이 겹치지 않는다.

## 단점

- **무엇**: 대비 부족.
  **어떤 문제를 만드나**: 필터·브레드크럼 `#545151` on `#181d21` = 2.16:1, INFO 라벨 `#85210f` on 주황 = 2.75:1, 시계 OFFLINE `#b53219` = 1.78:1, 문의 카드 흰 12 px on 주황 = 3.44:1. 모두 본문 기준 4.5:1 미달. 특히 "Filter" 버튼은 이 사이트의 유일한 목록 조작인데 가장 흐리다.
- **무엇**: 인트로의 조작 단서.
  **어떤 문제를 만드나**: 커서 알약은 마우스가 있어야 보인다. 터치 기기에서는 쇼릴과 띠만 보이고 "탭하면 들어간다"는 표시가 없다. 키보드는 sr-only "Watch our showreel" 버튼 하나뿐이라 Tab 으로 들어가도 진입 방법을 알기 어렵다.
- **무엇**: 목록 링크 수.
  **어떤 문제를 만드나**: 행마다 사진 하나하나가 같은 케이스로 가는 링크라 첫 행에만 링크 29개(복제 세트는 `tabindex=-1` 이지만 원본 세트만 해도 수십 개). 키보드 사용자는 케이스 9개에 닿기 위해 200개 넘는 Tab 을 거친다.
- **무엇**: 성능.
  **어떤 문제를 만드나**: 호버마다 행의 모든 사진(복제 포함 최대 62개)의 width·height 가 400 ms 동안 바뀌어 매 프레임 레이아웃 계산. 띠 WebGL 은 포인터가 움직이는 동안 띠 전체 글자를 매 프레임 다시 그린다.
- **무엇**: 문의 경로 중복.
  **어떤 문제를 만드나**: 시계 버튼(메일), INFO 의 메일, 케이스 사이드바 문의 카드, 끝 푸터 주황 띠, 서비스 모달 하단 띠 — 같은 메일 주소가 한 화면에 최대 3곳. 위계 없이 반복된다.

## 수정안

- **어디를**: 대비
  **어떻게**: `#545151` → `#8a8484`(4.62:1), 주황 위 라벨·상태 → `#43100a`(4.63:1), 주황 위 작은 흰 글자 → 검정(5.41:1), 호버는 색 대신 밑줄 — 모작에 적용.
  **왜 나아지나**: 모든 글자가 4.5:1 이상, 인상(흐림의 위계)은 유지.
- **어디를**: 인트로 진입
  **어떻게**: 터치 기기(`hover: none`)에서는 띠 아래 12 px 에 "Tap to enter" 를 3 초 뒤 페이드인. 키보드는 Enter/Space/↓ 로 진입(모작에 적용 — 접근성 최소선).
  **왜 나아지나**: 입력 방식과 관계없이 진입 방법이 보인다.
- **어디를**: 목록 링크
  **어떻게**: 사진 링크는 `tabindex=-1` + `aria-hidden`, 행당 초점은 캡션의 이름 링크 하나로.
  **왜 나아지나**: 케이스 9개 = Tab 9번(+ View project 9번).
- **어디를**: 행 확대
  **어떻게**: 행 높이만 `grid-template-rows` 로 바꾸고 사진은 `scale(1.2)` + 트랙 `gap` 을 같은 비율로 줄이는 계산(15 / 1.2 = 12.5)을 트랙 전체 `scale` 로 보정.
  **왜 나아지나**: 화면은 같고 사진 62장의 레이아웃 재계산이 없어진다.

## 재현하면서 배운 것

- 인라인 스타일을 "처음 값·마지막 값"만 남기는 기록으로는 곡선을 알 수 없다. 페이지에 rAF 로거를 심어 매 프레임 `getBoundingClientRect` 를 남기니 진입·덮개·INFO 곡선이 전부 나왔다. 이번 모작의 모션 수치는 거의 이 방법으로 얻었다.
- 모션 비교표의 빨간 줄은 대부분 "키프레임 이름이 다른 같은 모션"이었다. 이름을 맞추는 대신 지속·이징·키프레임을 줄마다 대조해 진짜 차이(쇼릴 영상 300 ms, 끝 마퀴 47.7 s, 사이드바 카드 700 ms)만 골라냈고, 그중 카드는 기능 자체를 빠뜨린 것이었다.
- 문서 높이 대조가 제일 빠른 구조 검증이다. 케이스 9개가 처음엔 94 % 였고, 원인은 `<figure>` 기본 여백 40 px 이었다. 지우자 9개 전부 원본과 같은 값이 됐다.
- Pinterest 의 동물·음식·정물 검색 결과는 AI 이미지가 대부분이었다. 감도는 Pinterest 가 맞지만 "실사" 조건이 붙으면 Unsplash 가 안전하다.

## 어긋난 채로 남은 것

- **쇼릴**: 원본은 고객 작업 영상 몽타주(유리 조형 3D 장면 포함). 모작은 사진 컷 전환 — 움직임의 양이 훨씬 적다.
- **영상 칸**: 소리·영상 없음. 클릭하면 사진이 바뀌는 대체.
- **케이스 끝 사진 마퀴 속도**: 원본 47.7 s 의 계산식을 못 찾아 "다음 프로젝트 행 속도 ×1.25"(42.8 s)로 둠.
- **시계 Online 규칙**: 원본이 언제 ONLINE 이 되는지 확인 못 함(측정 시각 전부 OFFLINE). 평일 9–19 시로 둠.
- **띠 찢김의 결**: 격자 72×10·반경 3칸·스프링 상수는 스크린샷을 보고 맞췄다. 원본 데이터 텍스처 크기(64×64 2D 캔버스로 추정)와 다를 수 있다.
- **인트로 키보드 진입**: 원본에 없는 동작(접근성 최소선으로 추가, SPEC 기재).
- **INFO 링크**: 가상 스튜디오라 설립자 LinkedIn·생태계 링크는 글자만, Whatsapp → Instagram.
